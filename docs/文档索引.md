# 文档索引（开发标准统一入口）

> **本文件是所有开发需求的唯一总入口。** 后续任何改动，都先经本索引定位规范、读完再动手，确保方向始终对齐项目标准。
> 最后更新：2026-08-05（终稿，已核对仓库实际文件，移除对不存在文件的引用）

---

## 〇、使用说明（操作协议）

**AI / 工程师收到新需求时的标准动作：**

1. **提取关键词**：从需求描述中拆出技术关键词（如"新增登录接口" → `API` + `鉴权` + `数据库`）。
2. **定位规范**：先查下方「三、检索指引（按需求类型）」，再查「四、关键词 → 文档映射」，得到该需求对应的**必读文档列表**。
3. **先读后写**：用 Read 工具打开这些文档，对齐命名 / 分层 / 提交 / 测试等约束，**未读规范不动代码**。
4. **开发 + 自检**：编码后对照《开发流程规范》§8「提交前 16 项检查清单」与《代码规范》§7「完成定义（DoD）」逐项核验。
5. **同步文档**：涉及接口 / 数据模型 / 架构的改动，同步更新对应文档（API 文档 / 数据库设计 / AI 架构设计）。

> 原则：**规范优先于直觉，索引优先于记忆。** 任何"我记得项目里是……"都应回到本索引指向的源文档确认。

> **接到任务后，先读根目录 `NOTES.md`**（AI 改动 / 踩坑 / 偏离 / 决策速览），再按下方步骤定位规范——尤其当任务涉及接口、数据库、RAG 或 Bug 修复时，`NOTES.md` 往往已记录相关上下文与已知坑。

## 一、文档分类体系

### 1. 代码规范（命名 / 格式 / 架构约定）
统一编码与提交标准，所有代码必须对齐。
- `docs/代码规范.md`（核心：分层、命名、类型注解、docstring、日志、异常处理、Git 提交、DoD）—— **必读**
- `docs/技术栈选型.md`（新增依赖 / 技术决策时的选型依据，参考级）

### 2. 开发流程规范（Git 工作流 / 阶段划分 / 质量门禁）
定义协作节奏、阶段职责与上线流程。
- `docs/开发流程规范.md`（角色职责矩阵、阶段 0–6、里程碑、分支模型、16 项检查清单、上线清单）—— **必读**
- `NOTES.md`（根目录，知识沉淀：关键决策 / AI 改了什么、为何改 / 踩坑 / 待办 / 偏离 —— 流程强制要求）—— **必读**

### 3. 业务领域规范（Business Domain）
理解系统要解决什么业务问题。
- `docs/业务流程说明.md`（注册登录、知识库管理、智能问答、反馈等流程与状态流转）—— **必读**
- `项目说明.md`（根目录，项目全貌、核心功能、技术栈总览、AI 架构图 —— 首读入口）—— **必读**

### 4. API 设计规范（API Design）
接口契约与代码层约定。
- `docs/API文档.md`（全部端点、请求/响应、错误码、SSE 事件序列、业务规则 —— 联调契约）—— **必读**
- `docs/代码规范.md` §1（api 层只做校验路由、不含业务逻辑的分层约定）

### 5. 测试与质量规范（Testing）
测试与质量保障要求。
- `docs/代码规范.md` §6（Spike 先行、单测、评测集要求）
- `docs/开发流程规范.md` §7（评测集与质量门禁）、§8（提交前检查清单）

### 6. 架构与技术参考（Reference）
实现细节与查漏补缺。
- `docs/AI架构设计.md`（RAG 架构、模块职责、流水线、Prompt 模板、检索策略、性能优化）—— **必读（改 RAG 必读）**
- `docs/数据库设计.md`（ER 图、8 张表结构、字段 / 索引 / 外键约束）—— **必读（改库必读）**

### 7. 运行与部署（Ops）
本地运行与演示。
- `运行指南.md`（根目录，环境、启动、配置、部署、故障排查）—— **必读（跑起来必读）**

> **规范符合性 / 代码审计**：本项目未单独产出"审计报告"文件；规范符合性由各规范文档自身约束 + 《开发流程规范》检查清单 + 《NOTES》偏离记录共同保障。如需审计视图，以《代码规范》+《开发流程规范》+《NOTES》为准。
