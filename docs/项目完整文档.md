### 1.2 当前待改进项（按优先级）

> 说明：以下 R1–R7 来自最新一轮代码复审，**目前（本文撰写时）均未落地**。

#### 🔴 R1（阻断级）· 前端 `done` 事件 stale closure，最终消息内容丢失

- **问题描述**：`frontend/src/pages/Sessions.tsx:105` 的 `done` 事件中 `content: streamingContent` 取自闭包快照。流式过程中 `setStreamingContent` 更新的是 React state，但 `onEvent` 闭包里的 `streamingContent` 变量不会同步，恒为初始值 `''`。
- **影响范围**：核心问答功能。用户会看到答案逐字流出，完成后气泡内容却被清空（比修复前更迷惑），**功能测试下表现为"答了等于没答"**。
- **涉及文件**：`frontend/src/pages/Sessions.tsx`
- **根因**：用 `useState` 变量在异步回调里读取"最新累积值"，违反了 React 闭包语义。
- **推荐优化方案**：改用 `useRef` 累加，`done` 时从 ref 取值：

```tsx
const streamingRef = useRef('');

// 在 send 的 onEvent 中：
if (event.type === 'content') {
  streamingRef.current += event.content;
  setStreamingContent(streamingRef.current);
} else if (event.type === 'done') {
  setMessages(prev => [
    ...prev,
    { id: Date.now(), role: 'assistant', content: streamingRef.current, created_at: new Date().toISOString() },
  ]);
  streamingRef.current = '';
  setStreamingContent('');
}
```
- **工作量**：小（约 5 行改动，0.5h）
- **预期收益**：核心问答流程闭环，可正常演示"流式输出并留存答案"
- **潜在风险**：低；注意把 `streamingRef.current` 在 `done` 后重置，避免下次会话串内容

#### 🟠 R2（高）· 每次请求重建模型客户端，存在性能瓶颈

- **问题描述**：`backend/app/services/chat_service.py:184-201` 在每次请求时 `new Embedder()` / `new VectorStore()` / `new LLMClient()`。
- **影响范围**：所有问答请求；若 `embedding_provider=local`（sentence-transformers），每次对话都会从磁盘重载数百 MB 模型，响应明显变慢、CPU/内存抖动。
- **涉及文件**：`backend/app/services/chat_service.py`
- **根因**：未做应用级单例/缓存，依赖在请求作用域内反复构造。
- **推荐优化方案**：模块级单例（或 FastAPI `startup` 注入）：

```python
from functools import lru_cache

@lru_cache(maxsize=1)
def get_embedder():    return Embedder()
@lru_cache(maxsize=1)
def get_vector_store(): return VectorStore()
@lru_cache(maxsize=1)
def get_llm_client():  return LLMClient()
```
`chat_stream` 内改为调用上述函数，而非现场构造。
- **工作量**：小（约 0.5h）
- **预期收益**：首请求后模型常驻，后续请求延迟大幅下降；大规模测试稳定
- **潜在风险**：低；注意 DashScope 客户端本身是有状态连接，单例更安全

#### 2.1.5 常见问题及解决方案

| 问题 | 原因 | 解决方案 |
|---|---|---|
| `git init` 后 `git status` 把 `.env` 也列进来了 | 未在 `git add` 前加 `.gitignore` | 先创建 `.gitignore` 再 `git add`；若已误加：`git rm --cached .env` |
| `ssh -T git@github.com` 提示 `Permission denied (publickey)` | 公钥未正确添加到平台，或用了错误的 key | 确认 `cat ~/.ssh/id_ed25519.pub` 内容已完整粘贴；多密钥时配置 `~/.ssh/config` 指定 `IdentityFile` |
| `git push` 要求输入用户名密码（HTTPS） | 远程用的是 HTTPS 地址 | 推荐改用 SSH 地址：`git remote set-url origin git@github.com:用户名/仓库.git` |
| 提交后姓名显示为未知 `User` | 未配置 `user.name/user.email` | 执行 2.1.2 的配置命令 |
| 不想每次都输 SSH 密码 | 生成密钥时设了 passphrase | 使用 `ssh-agent` 缓存：`eval $(ssh-agent)` && `ssh-add ~/.ssh/id_ed25519` |

### 2.2 LLM API Key 获取与配置

本项目 LLM 默认走 **DashScope（阿里云百炼）**，当前阿里云 LLM 服务可用，直接使用默认配置即可。

#### 2.2.1 获取 DashScope API Key

1. 登录阿里云控制台，进入 **百炼（Model Studio）** 控制台：https://bailian.console.aliyun.com
2. 首次使用需 **开通模型服务**（按页面引导开通，部分模型免费额度可用）。
3. 进入 **API Key 管理**（通常位于控制台右上角头像 → API Key，或"管理中心 → API Key"）。
4. 点击 **创建 API Key**，复制生成的 `sk-xxxxxxxxxxxxxxxx` 字符串。
5. （可选）确认账户有可用额度；若调用返回 401/429，见下方 FAQ。

#### 2.2.2 配置到项目

将 Key 写入 `.env`（见 2.3 生成 `.env` 后）：

```env
LLM_PROVIDER=dashscope
DASHSCOPE_API_KEY=sk-你的实际key
```

无需改代码——`backend/config.py` 通过 `pydantic-settings` 读取环境变量，默认即 `dashscope`。

#### 2.2.3 本地备选方案（无云端/离线场景）

若无法使用云端，可切到本地 **Ollama**：

```bash
# 安装 Ollama 后拉取模型
ollama pull qwen2.5:7b
```

```env
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=qwen2.5:7b
```

> 注意：Embedding 在 `config.py` 中仅支持 `dashscope` 或 `local`（sentence-transformers，对应 `LOCAL_EMBEDDING_MODEL=bge-small-zh-v1.5`），**没有 Ollama embedding 选项**。本地离线需 `EMBEDDING_PROVIDER=local`。

#### 2.2.4 常见问题及解决方案

| 问题 | 原因 | 解决方案 |
|---|---|---|
| 调用返回 `401 Unauthorized` | API Key 错误或为空 | 确认 `DASHSCOPE_API_KEY` 已填入 `.env` 且未被覆盖；重新在百炼控制台创建 Key |
| `429 Too Many Requests` | 触发限流或额度不足 | 检查账户额度；降低并发；必要时升级套餐 |
| `404 / model not found` | 模型名不匹配 | LLM 用 `qwen` 系列；Embedding 用 `text-embedding-v3`；确认该模型在账户已开通 |
| Ollama 连接 `Connection refused` | Ollama 服务未启动 | 先运行 `ollama serve`（或桌面端常驻），确认 `:11434` 可访问 |
| 本地 embedding 首次很慢 | sentence-transformers 首次下载模型 | 首次 `pip` 后会缓存；之后复用。注意会引入 torch 依赖（体积大） |

#### 2.3.3 常见问题及解决方案

| 问题 | 原因 | 解决方案 |
|---|---|---|
| 后端启动即报 `Can't connect to MySQL server` | 本机未运行 MySQL，或默认 `localhost:3306/root/空密码` 不匹配 | 启动本地 MySQL；或在 `.env` 中改 `DB_HOST/PORT/USER/PASSWORD` 指向实际实例 |
| 想换成 SQLite 但改 `DB_*` 无效 | `database_url` 在 `config.py` 中被硬拼成 `mysql+pymysql://...` 前缀，仅靠 env 无法切换 | 需改代码：将 `database_url` 改为根据 `DB_TYPE` 分支；并改写 `init_db.sql` 的 MySQL 专有语法（见下） |
| `init_db.sql` 在 SQLite 下报错 | 含 `ENGINE=InnoDB`/`AUTO_INCREMENT`/`ENUM`/`ON DUPLICATE KEY` 等 MySQL 专有语法 | 改用 `Base.metadata.create_all(engine)` 建表；或保留 MySQL 不切换 |
| Chroma 报 `sqlite3 version too old` | 运行环境 SQLite < 3.35 | 升级 Python/SQLite；或使用较新 Python（Windows + 现代 Python 一般无碍） |
| CORS 报错 `No 'Access-Control-Allow-Origin'` | 前端端口不在 `CORS_ORIGINS` | 把前端实际端口加入 `CORS_ORIGINS`（如 `http://localhost:5173`） |
| 改了 `.env` 不生效 | 程序已用默认值缓存 | 重启后端进程；确认 `.env` 位于 `backend/` 目录且文件名正确 |
