# 开发流程规范

> 版本：v1.0（终稿）　最后更新：2026-08-05
> 适用范围：AI 智能客服系统（FastAPI + React/TS + MySQL 8.0 + Chroma + DashScope）
> 配套文档：《代码规范》（分层/命名/提交/DoD）、《文档索引》（规范统一入口）、《NOTES》（知识沉淀）

---

## 0. 概述

本规范定义从**需求**到**上线交付**的完整研发流程、阶段划分、角色职责与质量门禁，确保所有改动可追踪、可评审、可回滚。

- **强制联动**：任何涉及接口 / 数据模型 / 架构 / RAG 的改动，须先经《文档索引》定位规范并阅读，再动手；编码后对照本规范 §8「提交前检查清单」与《代码规范》§7「完成定义（DoD）」自检，最后同步更新对应文档。
- **红线（不可逾越）**：前端零大量自定义 CSS（统一 Ant Design 默认样式）；SSE 必须用 `fetch + ReadableStream`（禁用 `EventSource`）；流式响应头带 `X-Accel-Buffering: no`；`vector_id` 作为删向量唯一键；绝不提交真实 `.env`/密钥。

## 1. 角色与职责划分

> 本项目为单人开发（应届生笔试场景），但流程上仍明确各阶段的**角色职责边界**——开发者在不同阶段切换"帽子"，并以自检清单替代团队评审，避免"自己审自己无约束"。

### 1.1 职责矩阵（RACI）

| 角色 | 需求分析 | 方案设计 | 环境/Spike | 核心开发 | 评测/QA | 文档 | 上线部署 |
|------|---------|---------|-----------|---------|--------|------|---------|
| **需求/产品负责人**（自审） | R/A | C | I | I | A | C | I |
| **架构/技术负责人**（自审） | C | R/A | A | C | C | C | C |
| **开发工程师** | C | C | R/A | R/A | R | R | C |
| **测试工程师**（自审兼任） | I | C | C | C | R/A | I | I |
| **运维/SRE**（自审兼任） | I | C | C | I | C | I | R/A |

> R=负责执行　A=对结果负责　C=被咨询　I=被告知
> 单人项目下，同一人承担多角色，但每阶段须按对应角色的"退出标准（DoD）"逐项核验，不得跳过。

### 1.2 阶段职责要点

- **需求分析**：拆解题面/真实业务诉求，界定"必须做 vs 可选扩展"，输出需求清单与优先级。
- **方案设计**：定架构、数据库 ER、API 契约、技术选型理由；重大偏离须记录于《NOTES》并说明理由。
- **环境/Spike**：验证 LLM / Embedding / 向量库 / 数据库可达性，不达预期不进入开发。
- **核心开发**：遵循《代码规范》分层（api/rag/services/framework）、类型注解、docstring、异常处理、结构化日志。
- **评测/QA**：维护 25 条评测集，跑质量门禁（§7），每次 RAG 改动后回归对比。
- **文档**：交付文档与代码严格一致（见 §10 清单），禁止"文档停留在早期草稿"。
- **上线部署**：依《运行指南》完成环境配置、种子数据、配置校验、启动验证、回滚预案。

## 2. 完整开发阶段（需求 → 上线）

每个阶段含 **目标 / 主要活动 / 关键产出 / 退出标准（DoD） / 责任角色**。

### 阶段 0　需求分析与技术选型
- **目标**：明确交付范围与边界。
- **活动**：解读笔试题评估标准；区分硬性功能与加分项；确定技术栈（DashScope qwen-plus / text-embedding-v3、Chroma、MySQL 8.0）。
- **产出**：需求清单、技术选型表（《技术栈选型》）。
- **DoD**：硬性功能 100% 明确；可选扩展单独标注；选型理由可追溯。
- **角色**：需求/产品负责人 + 架构负责人。

### 阶段 1　方案设计（架构 / 数据库 / API）
- **目标**：在编码前固化契约，降低返工。
- **活动**：画 RAG 链路架构图；设计 8 张表 ER 与索引；定义 REST 端点、请求/响应、错误码、SSE 事件序列；设计 Prompt 模板与检索策略（阈值/Top-K）。
- **产出**：《AI架构设计》《数据库设计》《API文档》《业务流程说明》《项目说明》。
- **DoD**：接口契约被前后端认可；数据模型经评审无歧义；Prompt 含引用约束与兜底逻辑。
- **角色**：架构负责人 + 开发工程师。

### 阶段 2　环境与基础能力验证（Spike）
- **目标**：消除"集成时才发现不通"的风险。
- **活动**：`spike` 三连（LLM 调用 / Embedding / Chroma 读写）；MySQL 初始化；认证链路打通。
- **产出**：可运行的最小骨架；`backend/init_db.sql`；`.env.example`。
- **DoD**：三连 spike 全部通过；DB 表结构就绪；无硬编码密钥。
- **角色**：开发工程师 + 环境/Spike 负责人。

### 阶段 3　核心功能开发
- **目标**：实现业务闭环。
- **活动**：loader（pypdf/txt/md/docx）→ 语义切分 → Embedding → Chroma → retriever（阈值 0.5 / Top-K=8）→ Prompt 拼装 → qwen-plus → SSE 真实流式；知识库上传/删除（幂等）；多轮（最近 3 轮）；配额（每日 100）；引用标注（「」+ snippet 原文 + 悬停）。
- **产出**：后端服务 + 前端页面；单测。
- **DoD**：单测通过；检索/问答/引用/配额/流式 5 类核心路径可演示。
- **角色**：开发工程师。

### 阶段 4　评测与质量保障
- **目标**：用数据证明质量达标。
- **活动**：跑 25 条评测集；指标对照门禁（§7）；意图门控 + 阈值双保险验证越界 query 拦截；回归对比上一轮。
- **产出**：评测报告（检索准确率/回答准确率/引用准确率/首字延迟）；《NOTES》记录。
- **DoD**：检索准确率 >80%、回答 >75%、引用 >90%、首字 <500ms；越界 query 零误召回。
- **角色**：测试工程师（自审兼任）。

### 阶段 5　文档与自测
- **目标**：交付物齐全且与代码一致。
- **活动**：逐字核对 8+ 份文档与真实代码；更新《NOTES》；跑 §8 清单。
- **产出**：11 份交付文档（§10）；自测记录。
- **DoD**：文档零陈旧表述；§8 清单 16 项全绿；《NOTES》含本次所有偏离与修复。
- **角色**：开发工程师 + 文档负责人。

### 阶段 6　上线与交付部署
- **目标**：环境可运行、可演示、可回滚。
- **活动**：依《运行指南》配置环境；`AUTO_INIT_KB=true` 启动自动向量化种子；启动验证全链路；准备回滚预案；提交并推送 `master`。
- **产出**：可运行系统 + 推送记录；部署/演示说明。
- **DoD**：首次启动无需手动灌库即可问答；全接口自测通过；密钥仅存 `.env.example`；已推送到 `origin/master`。
- **角色**：运维/SRE（自审兼任）+ 开发工程师。

## 4. 分支与提交规范

- **分支模型**：保护分支 `master`；功能开发走 `feature/<主题>` 本地分支，完成后合并并推送 `master`（单人项目，无独立 dev 分支）。
- **Commit 格式**：`type(scope): subject`，type ∈ {feat, fix, refactor, docs, test, chore}，subject 简明动宾。
- **合并前自检**：对照 §8 清单与《代码规范》§7 DoD；功能分支合入前 `git diff` 自查，无遗留 `print`/`TODO`/`FIXME` 与生产无关调试代码。
- **禁止**：提交真实 `.env`、密钥、超大二进制；强制 `-f` 推送到保护分支。

## 6. 知识沉淀：NOTES.md（已建立）

> **状态：已建立并持续维护**（根目录 `NOTES.md`，本规范早期版本曾标注"缺失"，现已补齐，非半成品）。

从第一天起维护根目录 `NOTES.md`，至少记录：
- **关键决策**：技术选型 / 阈值 / 架构偏离的"为什么"（面试官重点提问项）；
- **AI 改动**：哪些代码由 AI 生成、你改了什么、为什么改；
- **踩坑与解决**：Chroma 版本差异、SSE 缓冲假卡顿、沙箱密钥遮蔽等；
- **待办与遗留问题**：未完成的规范整改、已知偏离、可选扩展。

模板：
```
## 2026-08-05
- 决策：AUTO_INIT_KB 改 true，启动即自动向量化种子（满足"启动即可问答"）。
- 踩坑：沙箱 rm 被 safe-delete 包装器拦截致 index.lock 无法删，改用 Python os.remove 删锁。
```

## 7. 评测与质量门禁

- **评测集**：维护 25 条问答用例（覆盖产品/退换货/FAQ/边界问题），记录期望答案与检索来源（`tests/eval/run_rag_eval.py`）。
- **质量门禁**：

| 指标 | 门槛 | 实测 |
|------|------|------|
| 检索准确率 | > 80% | 88% ✅ |
| 回答准确率 | > 75% | PASS ✅ |
| 引用准确率 | > 90% | PASS ✅ |
| 首字延迟 | < 500ms | PASS ✅ |
| 越界 query 误召回 | 0 | 0 ✅ |

- **回归**：每次 RAG 改动后跑评测集，对比上一轮分数，劣化须回退或说明。

## 8. 提交前检查清单（16 项）

1. `ruff check` / `npm run lint` 0 错误（本地自查，非 CI 强制）
2. `tsc` 无类型错误
3. 后端 `/docs` 所有接口可测通
4. 前端 SSE 用 `fetch + ReadableStream`（非 EventSource）
5. 响应头含 `X-Accel-Buffering: no`
6. 上传文档 → Chroma 有向量 → MySQL 有 chunk 记录
7. 删除文档后 MySQL 与 Chroma 同步清空（无孤儿向量）
8. 空检索走降级提示，不幻觉
9. 配额超限返回 429 且有提示
10. JWT 过期/无效返回 401 跳登录
11. 消息长度 > 500 被拒
12. 引用 snippet 非空、可溯源、存完整原文
13. 11 份文档齐全且与代码一致（无陈旧表述）
14. `NOTES.md` 已更新（含本次决策/踩坑/偏离）
15. `.env` 未入库，仅 `.env.example`
16. 已推送到 `origin/master`
